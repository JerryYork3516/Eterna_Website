## 1. 内容体系目标

Website 内容体系必须同时做到：

1. 让普通公众理解 Eterna、数字居民和当前产品；
2. 让每项定义、产品事实和公开状态可追溯到权威来源；
3. 明确区分当前事实、正在开发、长期愿景和研究探索；
4. 让中文和英文保持事实一致、表达可本地化；
5. 支持未来新增产品和真实内容类型，而不改变 Eterna 根定位；
6. 对缺失、过期或失去授权的内容进行阻止发布、修正、撤回或明确标记。

Website 只承担公开表达和入口职责，不成为 Eterna、数字居民或产品定义的原始事实源。

## 2. 内容类型

| 内容类型 | 内容职责 | 主要权威来源 | 允许的事实状态 | Website 1.0 是否必须存在 |
| --- | --- | --- | --- | --- |
| Eterna Root Expression | 用适合公众的方式解释 Eterna 的使命、总体性质及其与数字居民的关系 | Node 1 固定的 Eterna 核心宪章、Universe 与仓库职责 | `CURRENT_VERIFIED`、`LONG_TERM` | 是；Home 与 About Eterna 必须承担，但不能新增上位定义 |
| Digital Resident | 解释数字居民是什么、不是什么、连续性与中心主体边界 | 《数字居民定义》及 Node 1 冻结基线 | `CURRENT_VERIFIED` | 是；必须有独立概念页 |
| Product | 说明产品服务对象、职责边界、与 Eterna 及数字居民的关系 | 对应 Product North Star、正式产品文档与批准来源 | `CURRENT_VERIFIED`、`IN_DEVELOPMENT`、`LONG_TERM` | 是；Website 1.0 当前覆盖 Studio、Aftelle，但各自只能发布有来源内容 |
| Product Status | 说明产品或能力当前真实成熟度、可用性和更新时间 | 对应产品仓库、发布记录或明确批准的状态输入 | `CURRENT_VERIFIED`、`IN_DEVELOPMENT` | 是；作为 Product 的受控属性，不单独构成页面 |
| Project Update | 记录产品级真实成果或经审核进展 | 正式发布记录、批准的产品状态来源 | `CURRENT_VERIFIED`、`IN_DEVELOPMENT` | 否；满足持续来源和维护条件后启用 |
| Long-term Vision | 说明长期使命、方向或 Universe 拓扑，避免被理解为当前承诺 | Eterna 核心宪章、Universe 及对应正式 North Star | `LONG_TERM` | 是，作为受控内容性质存在；不要求独立页面，也不在首页完整展开 |
| Research | 说明尚处研究探索阶段的公开工作 | 经批准公开的正式研究来源 | `RESEARCH` | 否；当前不建立栏目 |
| About / Project Information | 说明 Eterna 当前项目性质及经批准的公开身份事实 | 经批准的项目或公司事实来源 | `CURRENT_VERIFIED` | 是；当前不得补写成熟公司信息 |
| Contact / Participation | 说明可被真实接收和处理的联系或参与场景 | 经批准的公开联系方式、接收责任与业务流程 | `CURRENT_VERIFIED` | 能力要求是；公开内容在 N5-GAP-02 和处理条件解决后启用 |
| Legal / Privacy | 说明个人信息收集、用途、接收方和适用权利 | 经授权的法律与数据治理输入 | `CURRENT_VERIFIED` | 条件式必须；实际收集个人信息前必须存在 |

内容类型不等于页面类型。Product Status、Long-term Vision 等可以作为页面中的受控内容单元，但必须保留清楚的状态和来源边界。

## 3. 内容权威来源

### 3.1 来源层级

| 内容范围 | 首要来源 | Website 使用边界 |
| --- | --- | --- |
| Eterna 使命与总体原则 | `Eterna_Docs main@25972b9a1c106710988a98961b77904ef2a1acc9` 中的 Eterna 核心宪章 | 形成审核后的公开表达，不改变原定义 |
| Eterna Universe | 同一冻结快照中的《Eterna Universe》 | 区分长期拓扑与当前已实现产品，不把完整拓扑变成当前 Sitemap |
| 数字居民 | 同一冻结快照中的《数字居民定义》 | 保留身份、连续性与中心主体边界，不以传播性简化重写定义 |
| Studio | Studio North Star v0.3 与正式产品状态来源 | North Star 提供方向和职责；当前能力仍需产品状态证据 |
| Aftelle | 上位正文已有高层边界及未来正式 Product North Star | North Star 缺失期间不补写完整定位、功能清单或价值主张 |
| 产品当前状态 | 对应产品仓库、发布记录或明确批准的版本化输入 | 必须记录版本、日期或审核记录，不能从 Legacy 推导 |
| Eterna 项目信息 | 经批准的公开项目事实来源 | 不推测法定主体、团队、地点、历史或合作关系 |
| 联系与参与 | 经批准的公开联系方式、接收责任和处理流程 | N5-GAP-02 未解决时不发布虚假入口 |
| Legal / Privacy | 经授权的法律与数据治理输入 | 必须与实际数据字段、用途、接收方和第三方处理一致 |

### 3.2 每项正式内容的最小治理信息

每项正式内容至少需要能够回答：

- 内容类型与事实性质是什么；
- 首要来源文件、版本、commit 或批准记录是什么；
- 当前事实责任人与公开审核责任是谁；
- 中文和英文对应内容是什么；
- 最近审核时间是什么；
- 哪种变化会触发复核或撤回。

以上是内容治理要求，不预设数据库字段、CMS schema 或具体工作流工具。

## 4. 内容状态

### 4.1 对外事实性质

| 状态 | 含义 | 可发布条件 | 禁止表达 |
| --- | --- | --- | --- |
| `CURRENT_VERIFIED` | 当前真实且已由可追溯来源确认 | 有当前来源、适用时间和公开审核 | 不得把历史状态或候选方案标成当前事实 |
| `IN_DEVELOPMENT` | 产品或能力正在开发，但尚不等于公开可用 | 有产品级批准状态与审核日期 | 不公开内部 Stage、技术债、仓库细节、未冻结方案或虚假发布日期 |
| `LONG_TERM` | 长期使命、方向、愿景或产品拓扑 | 有上位或 Product North Star 支持，并明确非当前承诺 | 不得与当前功能列表、可用入口或近期交付承诺混写 |
| `RESEARCH` | 已获准公开但仍属于研究探索 | 有正式研究来源和公开授权 | 不得写成在研产品承诺、已验证能力或必然路线 |

状态名称是内容治理代码；最终公开标签可以自然本地化，但语义必须一一对应。一个页面可以包含不同状态的内容，但每项关键主张必须能被明确归类，不能以页面整体语气掩盖差异。

### 4.2 发布生命周期

事实性质与发布生命周期是两个不同维度：

| 生命周期 | 含义 |
| --- | --- |
| `DRAFT` | 正在编写，不能作为正式 Website 内容 |
| `REVIEW_REQUIRED` | 来源、事实、双语或公开范围仍待审核，不能发布为正式事实 |
| `PUBLISHED` | 来源、双语、状态和公开范围已经批准，可进入 Website |
| `WITHDRAWN` | 已过期、失去授权或被上游替代，不再作为当前公开内容 |

以上状态只是 Website 内容治理语义，用于表达内容是否具备发布资格及是否仍然有效；不代表 Website 1.0 必须实现完整 CMS 工作流、审批系统或状态机。

内部文档的 `FROZEN`、产品仓库 Stage 编号或工程状态不得直接成为对外内容标签。

## 5. 中文 / 英文对应关系

1. 每项核心正式内容必须有唯一的中英文配对身份；配对关系不依赖标题或 URL 猜测。
2. Website 1.0 的 6 个当前页面组必须形成一一对应的中文和英文版本。
3. 两种语言可以调整句式、术语解释顺序和文化语境，使表达自然；不得改变定义、产品职责、状态、日期、来源或行动可用性。
4. Eterna、Digital Resident、Studio、Aftelle 等核心术语应使用经过审核的对应表，不在单页内临时创造不同译法。
5. 上位事实、产品状态或公开授权变化时，中英文必须作为一组进入影响检查。
6. 核心页面任一语言未通过审核时，配对内容不得作为完整正式版本上线。
7. 已发布内容发生事实变化而某一语言尚未更新时，不得保留错误旧译；应撤回受影响表达，待双语复核后重新发布。
8. 不使用机器翻译自动填补缺失版本，也不把另一语言正文静默展示为本语言页面。

URL 使用 `/zh`、`/en` 对等前缀和相同 slug。语言选择必须指向已审核的对应内容；若条件式内容没有可发布的对应版本，不得创建空 URL 或伪造对应页。具体 i18n 技术留给 Node 9。

## 6. 当前事实与长期愿景边界

| 内容性质 | Website 应如何表达 | 不得如何表达 |
| --- | --- | --- |
| 当前事实 | 说明来源适用的对象、当前状态和审核时间 | 用永久性语气把当前阶段固化为 Eterna 最终定义 |
| 正在开发 | 只说明经批准公开的产品级阶段或真实成果 | 公开内部 Stage、技术债、仓库实现或未冻结方案 |
| 长期愿景 | 明确其方向性、长期性和与当前能力的差异 | 与当前可用功能、产品入口或发布日期混写 |
| 研究探索 | 明确研究属性、证据范围和不确定性 | 包装为产品承诺、路线确认或已经实现 |

边界规则：

- Eterna 总体使命可以稳定存在，但产品现状必须单独取证；
- Universe 长期拓扑不能自动变成当前产品目录；
- Studio North Star 支持职责与方向，不自动证明当前所有能力；
- Aftelle 只能采用现有高层边界和另行验证的当前事实；
- Website 不能用营销简化覆盖 Resident、Studio、Aftelle、Runtime Core、数据权威和身份治理之间的边界；
- 当前没有证据的内容保持 GAP，不以 “Coming soon” 代替事实。

## 7. 更新与失效原则

### 7.1 复核触发条件

出现以下任一情况时，相关中文和英文内容必须进入复核：

- 上位文档发布正式新版本、替代版本或语义变化；
- 产品状态、可用能力、发布日期或公开入口变化；
- 内容的公开授权、责任人或适用范围变化；
- 联系方式、数据字段、接收方或第三方服务变化；
- Legal / Privacy 输入变化；
- 时间敏感内容到达预定复核点，或来源已无法确认。

### 7.2 处理规则

1. 先确认新来源和受影响内容范围，再修改公开表达。
2. 定义、产品边界、状态和日期必须完成事实审核；中文和英文必须完成一致性审核。
3. 无法确认仍然有效的内容不得静默保留为 `CURRENT_VERIFIED`。
4. 被替代或失效的内容应更正、撤回或明确归档；不得继续参与当前产品描述和 metadata。
5. 紧急纠错可以先撤回错误内容，但不能用未经审核的替代文本填补。
6. Update 类内容如未来启用，必须保留发布日期、事实状态和失效边界；历史内容不得伪装为当前状态。

本节定义治理结果，不决定 CMS、自动化、审批软件或技术实现。

## 8. GAP

### 8.1 Node 5 保留 GAP

| GAP | 当前事实 | 内容体系限制 |
| --- | --- | --- |
| `N5-GAP-01` | Eterna 正式公司法定主体 / 对外公司名称尚未确定 | About Eterna 只能使用获批项目事实，不发布未经审核的主体名称或公司介绍 |
| `N5-GAP-02` | Eterna 当前可公开使用的联系方式尚未确定 | Contact / Participation 不得上线虚假地址、无人处理入口或默认继承 Legacy 联系链路 |

### 8.2 继承的上游限制

- Aftelle 正式 Product North Star 缺失：限制完整产品定位、功能清单和价值主张；
- 正式品牌规范缺失：限制品牌语言、Logo、视觉和语调的正式化；
- 当前产品可用性与公开能力清单缺失：限制 `CURRENT_VERIFIED` 能力声明和产品动作；
- 正式公共信息发布治理尚未形成：本文件只定义最小治理结果，不补写组织或工具。

这些限制不由 Website 文案、Legacy 内容、聊天记录或参考网站补齐。

## 9. 对 Node 7–9 的约束

### Node 7 — Design System

- 必须支持中文、英文及四类事实性质的清楚表达；
- 不得用颜色或动效作为状态和内容边界的唯一载体；
- 不得把 Legacy Aurora、圆形标记、玻璃样式或参考网站视觉提升为正式品牌规则；
- 品牌规范 GAP 未解决前，应区分临时设计决策与正式品牌事实。

### Node 8 — Product Design

- 必须遵守已确定的页面职责和层级，不把首页重新设计为完整 Universe 说明书；
- 必须让产品状态、来源性质和当前／长期边界可理解；
- 不得用空页面、虚假 CTA、登录入口或 “Coming soon” 填补缺失内容；
- Contact、Privacy、Updates 等条件式能力只能在启用条件成立后进入实际体验。

### Node 9 — Technical Architecture

- 必须支持中英文对应地址、规范内容身份、页面级 metadata、sitemap / robots 和稳定引用；
- 必须支持来源、审核状态、事实性质、更新时间和内容失效的治理结果；
- 必须保证未审核或已撤回内容不会被误发布为当前事实；
- 不得因 Legacy 使用 React、Vite、OGL 或 Airtable 而默认继承；
- 本文件不选择技术栈、CMS、Hosting、Analytics、API 或 i18n 实现。
