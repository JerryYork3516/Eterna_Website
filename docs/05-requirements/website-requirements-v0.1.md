## 1. 文档目的与输入

### 1.1 目的

本文件将 Website 1.0 的产品目标转化为可判断、可验证的需求，为后续信息架构、设计系统、产品设计、技术架构和开发计划提供边界。

需求采用以下分类：

| 分类 | 含义 |
| --- | --- |
| `MUST` | Website 1.0 首版必须满足；不满足即不具备当前验收条件 |
| `SHOULD` | 重要但允许首版有限缺失或后置；缺失时必须记录理由和影响 |
| `COULD` | 满足真实内容、需求和治理条件后允许加入；不阻塞 Website 1.0 |
| `OUT_OF_SCOPE` | Website 1.0 当前明确不做，或不在 Node 5 决定 |

“支持某类内容”表示 Website 需要具备相应的信息职责和治理边界，不等于本节点决定页面、栏目、导航或实现。

### 1.2 输入优先级

1. `docs/01-positioning/`：Node 1 上位输入基线与 Website 定位，优先级最高；
2. 本任务明确给出的 Node 5 产品决策；
3. `docs/02-existing-site-scan/`：旧站事实输入；
4. `docs/03-legacy-audit/`：旧站问题、风险和复用边界；
5. `docs/04-reference-study/`：只提供方法性参考，不构成 Eterna 需求来源。

Legacy 文案、页面和功能不得反向覆盖 Node 1。Node 4 案例不得直接转化为 Eterna 页面、导航或视觉。

## 2. Website 1.0 核心目标

Website 1.0 的核心目标是：

1. 让普通公众和潜在用户准确理解 Eterna；
2. 让访问者理解 Eterna 与数字居民的关系；
3. 让访问者了解有真实证据支持的当前产品；
4. 让访问者能够继续探索经过审核的产品、企业或相关内容；
5. 建立能够长期扩展、保持来源可追溯的企业主站能力。

Website 1.0 暂不以注册转化为核心目标，也不以完整解释 Eterna Universe、展示所有未来平台或推动单一产品转化为核心结果。

## 3. 用户与使用目标

### 3.1 主要用户

普通公众与潜在用户优先。Website 必须帮助他们：

- 在缺少 Eterna 背景知识时理解 Eterna；
- 理解数字居民是中心主体，而不是模型、Prompt、临时 Agent、角色卡或单次会话；
- 区分当前产品事实、开发中状态与长期愿景；
- 找到可信的继续探索或联系能力。

### 3.2 次级用户

次级用户包括创作者、Resident Designer、开发者、研究者和潜在合作方。Website 必须允许他们识别与自己相关的正式信息或联系能力，但 Node 5 不定义详细 Persona、用户旅程或转化漏斗。

### 3.3 非核心目标

- 不把注册、登录、下载或立即体验作为 Website 1.0 核心目标；
- 不让 Website 代替 Studio、Aftelle、Runtime 或产品文档；
- 不让首页承担完整 Eterna Universe 的解释任务；
- 不以展示尽可能多的产品、研究或内容为成功标准；
- 不从 Legacy 表单的存在推导必须沿用同一业务流程。

## 4. MUST

### 4.1 用户与企业定位

| ID | 需求 | 验收判断 |
| --- | --- | --- |
| `MUST-001` | Website 必须以普通公众和潜在用户为首要访问者，并兼顾创作者、开发者、研究者和合作方的次级信息需求。 | 核心内容无需内部或工程背景即可理解；次级用户能识别相关正式信息或联系能力，但不要求空栏目。 |
| `MUST-002` | Website 必须支持“理解 Eterna、了解当前产品、继续探索”三个核心结果，且不以注册、统一账户、购买或下载为首版验收前提。 | 三个结果均可通过正式内容或真实能力完成。 |
| `MUST-003` | Website 必须准确解释 Eterna、数字居民及二者关系，并保持数字居民为 Universe 中心主体。 | 定义性表达可追溯到 Node 1；不把 Eterna 或数字居民缩减为 App、模型、网站、Prompt、Agent 或单次会话。 |
| `MUST-004` | Website 必须保持 Eterna 总品牌高于 Studio、Aftelle 和任何未来单一产品。 | 任一产品内容均不会取代 Eterna 根定义，也不把单一产品称为 Eterna 的全部。 |
| `MUST-005` | Website 必须能够承载经过审核的正式企业信息。 | 公司信息缺失时保留 GAP，不以推测、聊天或 Legacy 文案补齐。 |
| `MUST-006` | Website 必须允许未来扩展产品和真实内容类型，而不重新定义 Eterna 根定位。 | 新增内容仍遵守 Node 1 的层级、来源与边界，不依靠空壳栏目或首页堆积制造扩展。 |

### 4.2 产品与内容

| ID | 需求 | 验收判断 |
| --- | --- | --- |
| `MUST-007` | Website 必须准确表达 Eterna Universe、数字居民、Studio、Aftelle、Runtime Core 等对象的关系；未来产品也必须说明其与 Eterna 和数字居民的关系。 | 不合并产品、运行、数据权威或身份治理职责，不以孤立产品表达反向修改体系。 |
| `MUST-008` | 所有产品事实必须绑定可追溯的产品来源、版本或审核记录。 | 无来源的功能、阶段、可用性或发布日期不得作为正式事实发布。 |
| `MUST-009` | 产品内容必须明确区分当前可用、开发中、长期方向和研究探索。 | 状态措辞一致，不把愿景、研究或内部候选写成当前已交付能力。 |
| `MUST-010` | Studio 和 Aftelle 只展示正式定义与真实证据支持的状态和能力。 | 不从 Legacy 推导新增能力；Aftelle Product North Star 缺失期间不猜测完整定位、功能清单或价值主张。 |
| `MUST-011` | Website 不得为未公开可用的产品创建虚假的体验、下载、购买或同等入口。 | 所有产品动作均与真实可用状态和接收能力一致。 |
| `MUST-012` | Website 必须支持 Eterna 企业、数字居民和产品三类核心正式内容。 | 三类内容具有可区分的信息职责和事实来源。 |
| `MUST-013` | 如公开产品进展或动态，内容必须是产品级真实成果或审核后进展，不得包含内部 Stage、技术债、仓库细节或未冻结方案。 | 抽样进展内容具有来源和审核记录，且不泄露或包装内部信息。 |
| `MUST-014` | Research、Developers、News、Support 只有存在真实内容、实际需求和维护责任时才能上线；不同内容类型必须保持职责边界。 | 不存在只有标题、占位文案或“Coming soon”的空壳内容；营销内容不覆盖治理事实。 |
| `MUST-015` | 在公开收集个人信息前，必须具备与真实处理一致的适用 Legal / Privacy 内容。 | 相关告知可访问，且覆盖实际字段、用途、接收方和第三方处理。 |

### 4.3 多语言与事实治理

| ID | 需求 | 验收判断 |
| --- | --- | --- |
| `MUST-016` | 中文和英文必须作为 Website 1.0 的正式内容版本。 | 核心正式内容同时具有经过审核的中文与英文版本。 |
| `MUST-017` | 两种语言必须经过人工编写或审核，可以合理本地化，但核心事实、产品状态和产品边界必须一致。 | 不以未经审核的机器直译作为正式内容；双语不出现事实、日期、状态或职责冲突。 |
| `MUST-018` | 上位事实或产品状态更新时，两种语言必须同步复核；正式翻译缺失时不得自动发布机器文本或把旧译文伪装成最新内容。 | 更新记录包含双语影响检查，缺失版本被阻止发布或明确处理。 |
| `MUST-019` | Eterna、Universe 和数字居民定义必须以 Node 1 冻结上位输入为事实源；当前产品状态必须来自对应产品仓库、发布记录或批准来源。 | 内容可追溯到文件、版本、commit 或正式状态记录；Website 不成为原始事实源。 |
| `MUST-020` | 每项正式内容必须具有明确的事实责任、审核责任、来源、审核状态和更新时间。 | 发布前可确认谁提供事实、谁批准公开以及依据的版本。 |
| `MUST-021` | 上位定义、产品状态、公开授权或时效变化时，相关内容必须复核；失效内容必须能够更正、撤回或标记。 | 变更不会静默保留过期表述，并有可验证的处理结果。 |

### 4.4 搜索、发现与分享

| ID | 需求 | 验收判断 |
| --- | --- | --- |
| `MUST-022` | 应公开发现的正式内容必须可被搜索引擎读取；具有独立信息职责的内容必须可被稳定引用。 | 核心内容不依赖不可抓取交互；外部引用可稳定指向目标内容而非临时 UI 状态。 |
| `MUST-023` | 独立正式内容必须具备准确的页面级 metadata、语言识别以及 sitemap / robots 管理能力。 | metadata 与内容、语言一致；可声明应发现和不应发现的公开范围。本要求不指定 URL 或实现。 |

### 4.5 联系、安全与隐私

| ID | 需求 | 验收判断 |
| --- | --- | --- |
| `MUST-024` | Website 1.0 必须保留真实联系或参与能力，可覆盖体验意向、合作和开发者联系等场景。 | 启用场景具有明确接收责任；GAP-02 未解决时不创建虚假联系方式或无人处理入口。 |
| `MUST-025` | 联系流程只能收集完成业务所需的最小数据，并在提交前告知用途、处理范围和适用隐私信息。 | 每个字段均有用途，非必要字段不强制；告知与实际接收方、第三方和处理一致。 |
| `MUST-026` | 公开联系能力必须具备防滥用、输入校验以及提交中、成功、失败和恢复反馈。 | 能处理自动化滥用、重复或异常请求；用户能判断提交结果及失败后的可用行动。 |

### 4.6 质量属性

| ID | 需求 | 验收判断 |
| --- | --- | --- |
| `MUST-027` | 核心内容和交互必须满足基础可访问性，包括键盘操作、语义结构、可见 focus、reduced motion、可读对比度和屏幕阅读器基础兼容。 | 不使用指针也能完成核心流程；语言、名称、角色、状态和错误可被理解；减少动态后内容完整，并通过对比度与人工辅助技术检查。 |
| `MUST-028` | Website 必须正式覆盖 Desktop、Tablet 和 Mobile，响应式变化不得丢失核心内容、操作、状态或来源信息。 | 三类设备均可完成核心目标；本节点不规定具体断点。 |
| `MUST-029` | 首屏和核心信息不得因视觉效果、动画、非必要媒体或第三方服务而严重阻塞。 | 可选资源延迟或失败时，核心内容和主要联系能力仍可访问。 |
| `MUST-030` | 动画、WebGL 和媒体必须允许暂停、减少或降级，并控制加载成本；核心信息不得依赖高性能视觉。 | 不支持或关闭相关能力后页面仍可用，核心事实不丢失，非必要资源不阻塞主要内容。 |
| `MUST-031` | Secret 不得进入客户端或公开内容；个人数据必须最小化；第三方服务必须审核用途、数据与失效影响；Analytics / Cookie 不得默认成为必选项；旧 Airtable 实现不得被默认继承。 | 发布产物和响应不含 secret；第三方接入与个人数据处理在上线前完成审核；未确认需求与合规条件时不依赖跟踪产品或旧 handler。 |

## 5. SHOULD

| ID | 需求 | 验收判断 |
| --- | --- | --- |
| `SHOULD-001` | 面向公众的核心说明应使用清晰、低门槛语言，并为必要术语提供上下文。 | 首次访问者无需内部文档即可理解核心概念。 |
| `SHOULD-002` | 核心内容应提供明确的继续探索方向。 | 用户理解当前内容后能识别下一步，但不要求注册转化。 |
| `SHOULD-003` | Website 应支持经过审核的产品级进展或动态；时间敏感内容应显示适当日期，并使用一致状态词。 | 用户可判断内容时效与产品成熟度；首版缺失该内容能力不阻塞核心企业与产品信息。 |
| `SHOULD-004` | 内容治理记录应支持内部追溯到审核人和变更原因。 | 争议内容能够还原批准过程。 |
| `SHOULD-005` | 联系场景应可随业务调整，提交后应提供可保留或可再次确认的结果反馈。 | 新增或停止场景不改变根定位，用户无需猜测请求是否被接收。 |
| `SHOULD-006` | 核心体验应在低带宽、媒体失败、脚本部分失败或非关键第三方服务失效时保持可理解。 | 主要事实和核心企业内容不会随可选依赖失败而消失。 |
| `SHOULD-007` | 发布前应包含键盘、屏幕阅读器、缩放和 reduced-motion 的人工验收。 | 自动检查之外保留人工验收记录。 |
| `SHOULD-008` | 适合分享的内容应支持准确、与品牌和语言一致的 social sharing 预览。 | 预览不使用错误、过期或跨语言信息；首版有限缺失可记录后置。 |
| `SHOULD-009` | 企业、支持、法律及其他真实内容类型应能在需要时独立增长。 | 增长不要求把全部低频内容放入核心首页叙事。 |

## 6. COULD

以下能力只有在存在真实内容、实际需求、责任人和审核流程时才允许加入：

| ID | 需求 | 启用条件 |
| --- | --- | --- |
| `COULD-001` | Research 内容能力 | 存在经批准公开的研究内容和持续维护责任。 |
| `COULD-002` | Developers 内容能力 | 存在真实开发者资源、稳定入口和维护责任。 |
| `COULD-003` | News / Progress 内容能力 | 存在持续、可审核、可失效的正式动态来源。 |
| `COULD-004` | Support 内容能力 | 存在真实支持范围、处理责任和更新机制。 |
| `COULD-005` | 未来账户入口需求预留 | 未来账户产品与职责被正式定义；Website 1.0 不实现统一账户。 |
| `COULD-006` | 站内搜索能力 | 内容规模与用户需求证明站内搜索具有实际价值。 |
| `COULD-007` | 历史进展或发布记录能力 | 有可公开、可维护且不暴露内部 Stage 的历史材料。 |
| `COULD-008` | 中文、英文之外的正式语言版本 | 建立相同的事实一致性、本地化和人工审核能力。 |

未满足启用条件时，不得使用占位页、空分类或“即将推出”替代真实内容。

## 8. 内容与事实治理要求

### 8.1 事实来源层级

| 内容类型 | 首要事实来源 | Website 权限边界 |
| --- | --- | --- |
| Eterna、Universe、数字居民定义 | Node 1 固定引用的 Eterna_Docs 上位输入 | 只做经过审核的公开表达，不创建新定义 |
| Studio 产品定义 | Studio North Star 与正式产品来源 | 不把规划、Legacy 或内部 Stage 当作当前公开能力 |
| Aftelle 产品定义 | 已冻结高层边界；未来正式 Product North Star | North Star 缺失期间不补写完整定位或功能清单 |
| 当前产品状态 | 对应产品仓库、发布记录或明确批准的状态输入 | Website 记录来源，不成为原始事实源 |
| 企业信息 | 经批准的公司事实来源 | GAP 未解决前不猜测主体、名称或联系方式 |
| 研究、开发者、动态、支持 | 对应内容责任人和审核来源 | 无真实内容、需求或维护责任时不上线 |
| 法律与隐私 | 经授权的法律与数据治理输入 | 不使用营销文案替代正式告知 |

### 8.2 内容生命周期

每项正式内容至少应完成：来源与公开范围确认、双语编写或本地化、事实与语言审核、发布状态记录，以及上游变化或时效触发后的复核、修正或撤回。

本节点只定义生命周期要求，不决定 CMS、工作流工具或组织实现。

### 8.3 状态表达

公开内容必须能够区分当前可用、正在开发、长期方向和研究探索。内部批准候选、内部 Stage、未冻结方案和仓库实现不得自动转换为公开状态。

## 9. 质量属性

| 质量属性 | 需求摘要 | 主要验收依据 |
| --- | --- | --- |
| 正确性 | 定义、产品关系和状态可追溯且不越权 | 来源与双语事实审查 |
| 可发现性 | 公开内容可被发现、稳定引用并具有准确 metadata | 搜索、引用和索引控制检查 |
| 可访问性 | 基础键盘、语义、focus、动效、对比度和屏幕阅读器兼容 | 自动检查与人工验收 |
| 响应式 | Desktop、Tablet、Mobile 均可访问核心信息与能力 | 多设备验收，不指定断点 |
| 性能韧性 | 核心内容不被视觉、媒体或第三方服务阻塞 | 降级、失败与低带宽场景验收 |
| 安全与隐私 | secret 隔离、最小收集、第三方透明与 Legal / Privacy 门禁 | 发布产物、数据流与治理检查 |
| 可维护性 | 内容来源、审核、更新和失效可追踪 | 内容生命周期记录 |
| 可扩展性 | 新产品和真实内容类型不改变 Eterna 根定位 | 后续 IA 与内容职责验收 |

本文件不设定框架级指标、具体性能预算、测试工具或实现方案。

## 11. 对 Node 6–10 的约束

### Node 6 — Information Architecture

- 从用户、内容职责、稳定引用和长期扩展需求出发；
- 不把 Legacy hash Section 或参考网站栏目直接当作目标结构；
- 具体页面、导航和 URL 由 Node 6 决定，不由 Node 5 预设。

### Node 7 — Design System

- 支持正式双语、可访问性、状态区分和多类内容；
- 不把 Legacy 或参考网站视觉直接设为 Eterna 规范；
- 正式品牌规范 GAP 未解决前，不把临时视觉提升为品牌事实。

### Node 8 — Product Design

- 服务“理解 Eterna、了解当前产品、继续探索”的核心结果；
- 不用注册、下载或虚假产品入口替代信息目标；
- 保留真实性、可访问性、响应式和降级要求。

### Node 9 — Technical Architecture

- 证明所选承载方式能够满足双语、治理、可发现性、性能、安全、隐私和扩展要求；
- 不因 Legacy 使用 React、Vite、OGL 或 Airtable 而默认继承；
- 目标技术架构只能在 Node 9 冻结。

### Node 10 — Development Plan

- 把 `MUST` 转化为可实施、可验证的开发与验收范围；
- `SHOULD` 未纳入时记录理由和影响；
- `COULD` 不挤占 `MUST`；
- `OUT_OF_SCOPE` 不被静默加入 Website 1.0。
